Six Key Rules (verified against pipeline YAMLs)

① Single RED injection point: Raw RED enters only at G1. All other stages inherit RED knowledge through the document ladder — never through re-injection of raw RED.

② Architecture order is ADR→NFR→SDD→SRD: Not SDD→NFR→ADR→SRD. Each stage formally consumes only what it needs: A1(ADR)=[frd], A2(NFR)=[frd,adr], A3(SDD)=[frd,adr,nfr], A4(SRD)=[sdd,frd,nfr].

③ KB Injection is static startup context, not live MCP queries: _card_context() (BM25) + _local_context() (pgvector) inject a static block before the agent starts. Applies to docs-target stages only. M2 (ui), M3 (api), M4 (policies), M5/M6 (tests), EA3/EA4/EA5/EA6 — all get no card injection.

④ HARD STOP gates at M1: SP-catalog.json (⑱) and schema-snapshot.json (⑲) must be pre-prepared before the pipeline starts. M1 halts immediately if absent. These same files are also produced/enriched at EA2 (DB wiring stage) for final DB configuration.

⑤ DB Integration is in the Epic Assembler (EA2), not Mini: It runs once after all EPIC branches are assembled — not per-EPIC in Mini Workspace.

⑥ Epic Assembler has 6 stages, not 5: EA1 Assembly → EA2 DB Integration → EA3 Local Deployment → EA4 UI Smoke → EA5 UI E2E → EA6 PR Merge.
Card Type → Respective Pipeline Stages (verified against pipeline YAMLs + stage_executor)
Typed cards are injected (via _card_context()) only into docs-target stages — Global G1–G6, Architecture A1–A4, and Mini M1 (LLD/TDDs). Each stage pulls the cards relevant to it (query-driven).
NO card injection at code/test/policy stages — M2 UI-code, M3 API-code, M4 Security-OPA, M5 API-test, M6 UI-smoke — and all Epic-Assembler stages. They build from the TDDs + domain-pack, so a card must land in the M1 TDD to influence generated code.

How & where the cards are created — re-kb-build invocation
The SCR/CMP/ENT/API/WF/BR/FR cards are created by the AIDLC-kb:kb-build agent inside the re-kb-build pipeline — not by the forward SDLC agents (those only consume them).
AspectValue (verified)
Workspace tierGlobal — tier: global, runs ONCE per application (not per-EPIC/mini)
Execution runnerServer-side (Bedrock worker / API process) — the kb-build stage has no required_runner. Contrast: Architecture A1–A4 and Mini M1 are required_runner: cli (local laptop).
What it doesReads corpus → LLM synthesises typed cards (cite-or-abstain, evidence locus required) → writes knowledge/<kind>/<ID>.md + graph.json + evidence-map.jsonl + cards.jsonl → kb-check gate → publish to CardStore
CardStore locationLocal disk kb_root_for = workspaces/<app>/kb/ (or FE_KB_ROOT). Also persisted to S3 as the kb artifact when FE_ARTIFACT_STORE=s3 — but agents read the local path, not S3.
Distributed implication: because re-kb-build runs server-side but the Architecture/UI/API design stages run on the local CLI, a distributed deployment must bridge the CardStore — via a shared FE_KB_ROOT (EFS/NFS/SMB), an S3 hydrate step, or co-location. Single-host deployments work out of the box (same kb_root_for).
Locations: pipeline → app/agentic_platform/pipelines/re-kb-build.yaml (agents repo)  |  skill → plugins/lib/uw/aidlc-kb/skills/kb-build/SKILL.md  |  orchestrator → plugins/lib/uw/aidlc-kb/agents/kb-orchestrator.md  |  gate → plugins/lib/uw/aidlc-kb/skills/kb-check/  |  runtime → worker/stage_executor.py (_materialise_corpus / _kb_gate / _publish_kb)
