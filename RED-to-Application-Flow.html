ⓘ How RED Information Reaches Mini Workspace Agents (M1–M7)
❶ Document Ladder (primary)
RED is injected only at G1 PRD via _fetch_graph_rules() or _local_context().

Knowledge is then distilled and structured through the pipeline:
RED → BRL-NNN (G1) → FR-NNN (G2) → SDD (A3) → SRD (A4) → EPIC → Feature → User Story → TDDs (M1)

By the time M1 receives user-story.md, business rules, workflow states, and component logic are already encoded with source citations (BRL-NNN → RED file:line).
Carries: ①②③④⑤⑥⑦⑧⑩⑪⑬⑭⑮⑯
❷ KB Prompt Injection (at agent startup — NOT live MCP queries)
The KB is built by a separate manually-triggered pipeline (re-kb-build.yaml) before the SDLC pipeline starts. It is NOT automatically gated as a prerequisite of uw-cr-global.

Two stores are populated: CardStore on disk (BM25 → _card_context()) and Postgres pgvector (vector search → _local_context()).

At each stage startup, the platform pre-assembles a static context block from these stores and injects it into the agent prompt — before the agent starts. This is NOT a live mid-run query.

mcp__kb__* tools ARE in every stage's allowlist, but the MCP server only launches when FE_KB_AGENT_TOOLS=mcp AND KB_BACKEND_ROOT env var is set. No agent prompt file explicitly calls these tools.

⚠ M2 (UI Code) and M3 (API Code) stages get NO card injection — _card_context() skips stages where target != "docs". These stages rely entirely on TDDs and domain-pack.
Carries: ⑥⑪⑫ via injected card/chunk context (docs-target stages only)
❸ Direct File Read (DB artifacts only)
⑱ SP-catalog.json and ⑲ schema-snapshot.json are NOT KB-indexed.

They are structured JSON files extracted directly from the non-production MS SQL database by the procedure-introspector and schema-reverse-engineer agents and stored as workspace files.

M1's springboot-tdd-designer reads them directly using the Read tool. If absent: HARD STOP — M1 halts immediately.
Carries: ⑱⑲ (SP signatures + DB table structure) — HARD STOP
Bottom line: RED is injected at G1 once. All downstream agents (M1–M7, EA1–EA5) access RED knowledge through (1) the document ladder (structured artifacts refined at each stage), (2) KB prompt injection — _card_context() (BM25 over CardStore) + _local_context() (Postgres pgvector) inject a static context block before the agent starts, docs-target stages only — or (3) direct JSON file reads (⑱⑲ only). No second raw RED injection; no always-on live MCP queries.

How & where the cards are created — re-kb-build invocation
The SCR/CMP/ENT/API/WF/BR/FR cards are created by the AIDLC-kb:kb-build agent inside the re-kb-build pipeline — not by the forward SDLC agents (those only consume them).
AspectValue (verified)
Workspace tierGlobal — tier: global, runs ONCE per application (not per-EPIC/mini)
Execution runnerServer-side (Bedrock worker / API process) — the kb-build stage has no required_runner. Contrast: Architecture A1–A4 and Mini M1 are required_runner: cli (local laptop).
What it doesReads corpus → LLM synthesises typed cards (cite-or-abstain, evidence locus required) → writes knowledge/<kind>/<ID>.md + graph.json + evidence-map.jsonl + cards.jsonl → kb-check gate → publish to CardStore
CardStore locationLocal disk kb_root_for = workspaces/<app>/kb/ (or FE_KB_ROOT). Also persisted to S3 as the kb artifact when FE_ARTIFACT_STORE=s3 — but agents read the local path, not S3.
Distributed implication: because re-kb-build runs server-side but the Architecture/UI/API design stages run on the local CLI, a distributed deployment must bridge the CardStore — via a shared FE_KB_ROOT (EFS/NFS/SMB), an S3 hydrate step, or co-location. Single-host deployments work out of the box (same kb_root_for).
Locations: pipeline → app/agentic_platform/pipelines/re-kb-build.yaml (agents repo)  |  skill → plugins/lib/uw/aidlc-kb/skills/kb-build/SKILL.md  |  orchestrator → plugins/lib/uw/aidlc-kb/agents/kb-orchestrator.md  |  gate → plugins/lib/uw/aidlc-kb/skills/kb-check/  |  runtime → worker/stage_executor.py (_materialise_corpus / _kb_gate / _publish_kb)

CardStore implication: re-kb-build and the Global stages (incl. G1 PRD) are server-side — they share the server’s kb_root_for, so PRD sees the freshly built cards automatically. In a distributed deployment those hosts differ, so the server-built cards must be bridged to the laptop via a shared FE_KB_ROOT, an S3 hydrate step, or co-location (single-host works out of the box).
